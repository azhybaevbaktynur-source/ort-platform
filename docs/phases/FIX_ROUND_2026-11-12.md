### 1a. `/ru/admin` shows "Что-то пошло не так"

**Role:** platform admin. **Steps (branch):** sign in with the code, open `/ru/admin`. With the backend up the
overview renders (13 users, metrics, "Требует внимания", quick actions, health line, recent exams); no console error,
no failing request. **Not reproducible anonymously on production** (admin only). The Next error boundary
(`src/app/[lang]/error.tsx`, `mascot.error.title` = the same words, with the mascot and "Попробовать снова") was

**Fault injection** (each API call failed one at a time with `page.route`, screenshots `admin_fault_*.png` in the
scratch run; the table is the evidence):

| Failing call | What the page shows |
|---|---|
| none | full overview |
| `/platform/summary` → 500 JSON | **whole overview replaced** by "Не удалось загрузить. Что-то пошло не так. Попробуйте ещё раз." + Повторить (`1a_admin_overview_summary_502_simulated.png`) |
| `/platform/summary` → 502 HTML (what Render's proxy answers while the service wakes up) | same |
| `/platform/summary` → network failure | same box with "Нет связи с сервером" |
| `/platform/summary` 25 s slow | full overview once it answers (no timeout) |
| `/platform/overview` → 500 | only the metrics row shows an inline error; the rest renders |
| `/platform/health` → 500 or aborted | health line says "Не удалось проверить"; the rest renders |
| `/platform/access/overview` → 500 | the "recent exams" card stays a skeleton forever (error swallowed, `AdminAccessUi.tsx:22`) |
| `/me/bootstrap` or `/me/lms` → 500 | full overview (the cached answer is used) |

**Cause.** `frontend/src/app/[lang]/admin/page.tsx:50-52`: `error && pending === null ? <ErrorState …/> : (all
cards)`. `error` is the admin shell's `GET /platform/summary` (`components/lms/admin/AdminShell.tsx:47-67`: one retry
after `RETRY_MS = 1500`, then the error is kept). A 5xx or non-JSON answer maps to code `unknown`
(`lib/lms/client.ts:79`), whose text is `lms.errors.unknown` = "Что-то пошло не так. Попробуйте ещё раз."
(`ru.json:217`). Why only on production and not every time: Render Free spins the service down after 15 minutes
(`docs/COSTS.md`, `PERFORMANCE_AUDIT.md` §3.5). On a cold visit the first requests get Render's 502/503 HTML; the
header and the admin navigation still render from the `sessionStorage` bootstrap cache (last round's SWR), so the only
visible symptom is this box, and both tries (0 s and 1.5 s) fall inside the ~30-60 s wake-up. The admission gate's
503 `server_busy` under load gives the same picture with another text. The summary endpoint itself is fine (1.2 s on
the branch; `/me/bootstrap` 4.0 s, `/platform/health` 1.4 s, `/platform/overview` 1.7 s, all measured from here to
Frankfurt; step 2 material).

**Fix (slice 1a, Opus).**
1. `admin/page.tsx`: remove the page-level gate. Pass the summary state into `NeedsAttention` (`pending`,
   `storageLevel`, plus a new `summaryError` + `onRetry`); that card shows its own inline `ErrorState` and the other
   cards render. Keep the `mfa_enrollment_required` redirect in `AdminShell` untouched.
2. `AdminShell.refresh`: retry schedule `[1500, 4000, 8000]` ms instead of one retry, and never clear a value that was
   already loaded (a background failure must not blank a card).
3. `RecentExamsCard` / `useAccessOverview`: keep the error and show an inline error with retry instead of an endless
   skeleton.
4. A small `CardBoundary` (React error boundary, one file in `components/lms/admin/`) around each overview card: a
   render crash in one card shows that card's error, never the page's boundary.
5. Tests: `frontend/e2e/admin-overview.spec.ts` gets three cases: `/platform/summary` answers 502 `text/html` → metrics,
   quick actions, health line and recent exams are visible and only "Требует внимания" shows an error with Повторить,
   which recovers after `unroute`; `/platform/access/overview` 500 → that card's error only; a card that throws (a
   test-only `?e2e_throw=` is not wanted: instead mock `/platform/overview` with a malformed body and assert the
   metrics card alone shows the error). Backend: `tests/lms/test_admin_mfa.py::test_the_admin_health_check` covers the
   health answer; add a case there (or in `test_platform_admin.py`) with the e-mail provider unset and
   `LMS_STORAGE_DRIVER=r2` without keys, asserting 200 with `ok: false` and both checks `ok: false`, so "one service
   down or not connected" is an answer the page can show, never an exception.
**Risk:** low, frontend only; the MFA gate path is shared with the shell and must keep its test (`admin-mfa-gate.spec.ts`).

### Better ideas

1. **1a: one "server is waking up" state for the whole app.** `client.ts` can map an HTML 502/503 (Render's wake-up
   page) to a code `server_starting`; `LmsShell` shows one quiet line "Сервер запускается, ещё несколько секунд…" and
   retries with backoff, reusing `useBackendWarmup`. The admin overview would then never see the failure, and neither
   would a student opening the app after lunch. Half a day on top of slice 1a; recommended, because every page has this
   failure mode and the owner will see it again elsewhere.
2. **1c: no stored state at all.** Show "approved" only while the teacher has no course of their own
   (`approved_notice` returns `None` once a teaching enrolment exists) and keep the 14-day cap: the newer teacher
   already has a course and would not see it. Simpler (no migration, no endpoint), but it is not "dismissible", and a
   teacher invited into an existing course never sees the confirmation. The stored dismiss is cheap enough; I recommend
   it, this is the fallback if the migration is unwanted this round.
3. **1b/1e: the Learning home should have its own URL** (`/learn` or `/home`) instead of `/courses?view=learning`.
   `?view=` is why `ViewSync`, `ViewParam`, the latch and three redirect rules exist, and why last round fought
   flicker on `/courses`. Not for step 1 (it touches every link), but it should be a decision in step 3a: then
   `/courses` is "my courses" in the area the person is in, and `coursesDefault` disappears.
4. **1b: decide the frame from the person for every unclaimed URL**, not from a list of "personal" routes: an
   unclaimed URL gets `learnsHere(me) ? "student" : "app"`. The list in the slice is the safe first step; the general
   rule is the end state and should be written into `shellKind.ts` with the check file as its spec.
5. **1b/3b: teachers in the catalog.** "Записаться" on a platform course is how a teacher silently becomes a
   teacher+student (1e). In step 3b the catalog for people who teach should offer "Открыть как ученик" (the existing
   Student view mechanism) rather than a real enrolment, or at least ask.
6. **1d: "Access and Pro" is an admin tool, not a course setting.** Everything on that tab for a platform course links
   to Admin → Pro / Платные экзамены; the exam link field is the only real setting. Consider moving the exam link into
   Admin → Courses → course detail and dropping the tab altogether; then course settings are the same for every course
   kind, which is where step 3a is heading.
