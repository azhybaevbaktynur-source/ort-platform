## 1. Accounts and roles

### 1.1 How it works today

- Everyone registers the same way, as a plain user.
- In the UI that user is treated as a student.
- To teach, the user opens "Become a teacher" and sends a request. A platform admin approves it. Only after that can they create courses.
- Inside a course, the role comes from the enrollment: `teacher`, `assistant` or `student`. One person can teach one course and study in another. This part already matches Canvas.
- Platform admins are set with `make_admin.py`. There is one today: you.

**Problems with this flow:**
1. A real teacher has to find a hidden "Become a teacher" link after signing up. Nothing asks "are you a teacher?" at the start.
2. You personally must approve every teacher. At 6,000 students and hundreds of teachers, that does not scale.
3. Schools cannot manage their own teachers. There is no idea of a school or organization.
4. There are no parent accounts, even though parental consent for under-14s is legally required (Phase 9, D5).
5. Some texts still say "Student (ORT preparation)", for example the sign-up labels.

### 1.2 How Canvas does it

1. **Roles belong to the enrollment, not the account** (verified in the Canvas source). There is no global "teacher" flag. A Canvas user is just a user. The roles are Teacher, TA, Designer, Student and Observer (a parent), plus custom roles defined per school account. We already copy this idea.
2. **Institutional Canvas** (universities and schools) has no self-registration at all.
   - The school's IT department creates the accounts, usually from its student records system.
   - Account admins create the courses and assign teachers to them.
   - Course creation by teachers is a setting, `teachers_can_create_courses`, and it is **off by default**. There are similar settings for students and for users with no enrollments.
3. **Canvas "Free for Teacher"** *(public docs)*:
   - The sign-up page asks "I'm a teacher", "I'm a student" or "Parent".
   - A teacher can create courses immediately, with no approval. The cost is that there is no vetting and the courses are private.
   - A student needs a course join code to sign up.
   - A parent needs a pairing code generated by the student.
4. **Accounts and sub-accounts**: Canvas has a tree such as University, then Faculty, then Department. Admins at each level manage their own part of the tree. That is how Canvas scales administration: a school admin approves that school's teachers, not one global admin.

### 1.3 Options for us

| | Option | Teacher experience | Control | Fit |
|---|---|---|---|---|
| A | **Keep as is**: everyone is a student, and teachers request approval later | Poor: the teacher has to find the link | Full; every teacher is vetted by you | Fine for a pilot; does not scale |
| B | **Choose at sign-up and apply**: "I'm a student / I'm a teacher". A teacher fills a short application during sign-up and is "pending" until approved | Clear from minute one | Full | Small change; good now |
| C | **Trust levels**: any verified user can create *private* courses with low limits (for example 2 courses, 40 students, a small storage quota, invite only). Approval is needed only to list a course in the public catalog and to raise the limits | Instant, like Canvas Free for Teacher | Partial: unvetted adults can reach minors through private courses | Grows fastest; risky with minors and the R2 free tier |
| D | **Organizations (lightweight Canvas accounts)**: a school or tutoring center is an organization with its own admins. Org admins invite and approve their own teachers, see their courses, and can join codes to the organization | Teachers join through their school | Delegated to the school | Needed once several schools use the platform |

### 1.4 Recommendation

**B now, D next, C only if demand appears. Keep the per-course roles exactly as they are.**

**What to add now (option B):**
1. **The sign-up form asks for a role**: "I'm a student", "I'm a teacher" or (later) "I'm a parent". This is only an *intent*. It sets the first screen after login and, for teachers, opens the application.
2. **A teacher application inside sign-up** with these fields:
   - full name;
   - school or organization;
   - subject;
   - city or region;
   - phone;
   - an optional note.

   The account works at once as a normal user. The ability to create courses turns on after approval, and an email (en/ky/ru) says so.
3. **Admin invites a teacher by email**. The invitee arrives already approved, with no request needed. This is useful for onboarding a partner school quickly.
4. **Course owners add co-teachers and assistants themselves**, by email, with no platform approval. This is a course role, which is the Canvas rule. A co-teacher invited this way can work in that course only. They cannot create their own courses unless they are approved.
5. **Clean up the texts**: "Student (ORT preparation)" becomes a neutral "Student", and similar.

**Next (option D, a lightweight version):**
- The tables would be `organizations` and `organization_members (role: org_admin | teacher)`.
- An org admin approves teachers for their organization. You approve organizations, not every teacher.
- There is no tree and there are no custom roles.

**Later:**
- **Observer (parent) role**: parents link to their child with a pairing code, see grades and give consent for under-14s. This ties in with Phase 9 privacy.
- **Why C is not recommended now**: unvetted adults could create private courses that minors join, and anyone could fill R2 storage. If we want C later, combine it with D: an organization vouches for its teachers.

## 2. How courses are structured

### 2.1 What a course is today

```
Course (title, description, languages, status draft/published/concluded,
        visibility private/catalog, enrollment mode, join code, limit, dates)
 ├─ People (enrollments: teacher / assistant / student)
 ├─ Question banks ─ Questions (versioned) ─ Passages
 ├─ Assessments (quizzes) ─ Sections ─ Items (question / passage group / random pick)
 │     └─ Published versions (snapshots) ─ Attempts ─ Answers
 ├─ Gradebook: submissions (one per student per assessment), categories with weights,
 │     late policy, overrides, release
 └─ Grading schemes (points, percent, bands, pass/fail, curve, lookup table)
```

Course tabs today: Home, People, Assessments, Grades, Bank, Settings.

### 2.2 What a Canvas course is

```
Course
 ├─ Home page (chosen: modules, a page, the syllabus, or activity)
 ├─ Modules ─ items: Page | Assignment | Quiz | Discussion | File | Link | Text header
 │     (prerequisites, "complete these items", unlock dates, sequential order)
 ├─ Assignments  ← THE gradable unit. Submission types: none (offline), text, file upload,
 │     link, media, quiz, discussion, external tool. Grouped into assignment groups with weights.
 ├─ Quizzes (a quiz is one kind of assignment), question banks
 ├─ Pages (wiki), Files, Syllabus, Announcements, Discussions, Calendar, Inbox
 ├─ Gradebook: one column per assignment (+ manual columns), rubrics, SpeedGrader
 └─ People (with sections), Outcomes, Settings
```

**The key structural difference.** In Canvas, an **assignment** is the general gradable thing, and a quiz is only one way to submit one. Here, the **quiz is the only gradable thing**: a grade row requires an assessment (`submissions.assessment_id` is required). So a teacher cannot:
- grade a homework essay uploaded as a file;
- enter a mark for an oral exam or class participation;
- grade anything that is not a quiz.

That is the main reason the platform feels like a test-prep site instead of a course platform.

### 2.3 How ORT-specific is the code, honestly

The **engine is general**:
- **Question types**: there are 7, in a pluggable registry: single choice, multiple answers, true/false, numeric, short text, essay, and comparison.
- **Content**: versioned questions and passages.
- **Exams**: sections with their own timers and rules, random picks from a bank, and free or forward-only navigation.
- **Timed attempts**: autosave, a server-owned timer, and a one-shot submit.
- **Grading**: grading schemes are data, not code (points, percent, bands, pass/fail, curves, lookup tables), plus weighted categories, late policy and overrides.

ORT itself is mostly data: two seeded courses and two grading schemes.

What makes it *feel* ORT-only is in four layers:

| Layer | What is ORT-shaped | Effect |
|---|---|---|
| **Missing course structure** | No modules, pages, files area, announcements, discussions or calendar. No gradable item other than a quiz | A course is just "a bank plus quizzes". This is the biggest gap |
| **Hard-coded exam presets** | `ort_main` and `ort_subject` are fixed in a database CHECK, in the API schema and in the frontend. ORT section times and rules are in code (`assessments/rules.py`). The importer and the assessment rules use different subject keys (`math_subject` vs `advanced_math`): a small existing bug | Adding another exam (SAT, IELTS, a school exam) needs a migration and code. Templates should be data |
| **Importer** | The CSV/bundle format is "ORT question bundle". It has fixed A-E columns and creates only single-choice and comparison questions | Teachers cannot bulk-import the other 5 question types |
| **UI defaults and branding** | Discussed in the paragraphs after this table | Every course looks like an ORT course |

The UI defaults and branding in detail:
- The app is named "ОРТ Подготовительная Платформа", with the "ОРТ" logo hard-coded on the auth pages. Email texts are hard-coded Russian ORT text.
- ORT section names (math_1, analogies, …) are suggested in every course's section and filter fields.
- Every reading passage gets ORT-style line numbers.
- The result page is the "ORT result view".

None of this blocks a general course technically. Together, though, it makes every course look like an ORT course.

The DB also fixes the languages to en/ru/ky. That is fine for Kyrgyzstan and is a regional choice, not an ORT one.

## 3. Proposed plan (to replace Phases 6–9 as currently ordered)

The current plan has Phase 6 (modules and pages), Phase 7 (enrollment forms), Phase 8 (practice and analytics) and Phase 9 (launch). I suggest reordering. Generalize first, then add the "assignment" concept, then structure. Modules need assignments to exist as module items, so assignments must come before modules.

| # | Phase | What it delivers | Size |
|---|---|---|---|
| **6** | **Generalize (de-ORT) + accounts B** | The parts are listed under the table | M |
| **7** | **Assignments and a general gradebook** | The parts are listed under the table | L |
| **8** | **Course structure** (the old Phase 6, extended) | The parts are listed under the table | L |
| **9** | **Organizations + enrollment** (option D + the old Phase 7) | Organizations with org admins; co-teacher invites; enrollment forms and applications; email invitations | M |
| **10** | **Practice, analytics, student tools** (the old Phase 8) | Practice by topic, mistakes notebook, course analytics | M |
| **11** | **Privacy, hardening, launch** (the old Phase 9) | Parent/observer role and consent, security review, load test, runbooks | M |

**Phase 6, Generalize (de-ORT) + accounts B:**
- A neutral platform name and logo, chosen by you. App name, metadata and email templates become i18n in en/ky/ru.
- Exam templates become data, with an `assessment_templates` table. ORT main and ORT subject become rows, not CHECK values.
- Section suggestions come from the course's own sections, with ORT names only inside ORT courses.
- Passage line numbers become an option per passage or section.
- The importer gets a general format covering all 7 question types; the ORT format stays as one profile of it.
- The subject-key bug is fixed.
- Sign-up role choice, the teacher application, admin teacher invites, and neutral texts.

**Phase 7, Assignments and a general gradebook:**
- An `assignments` table becomes the gradable unit, with these submission types:
  - none (offline or manual grade);
  - text;
  - file (PDF or image, within R2 limits);
  - quiz, which links an existing assessment.
- Submissions point to an assignment, and the quiz becomes one kind of assignment. Existing ORT grades migrate one-to-one.
- Manual grade entry, simple rubrics, and teacher feedback with a file.
- Assignment groups use the existing weighted categories.

**Phase 8, Course structure (the old Phase 6, extended):**
- Modules with items: page, assignment, quiz, file, link, header. Prerequisites, completion requirements and unlock dates (gating).
- Pages (wiki) and a course Files area.
- Announcements.
- A choice of course home page (modules, a page, or the syllabus).
- Discussions are optional here, or later.

After Phase 8, an ORT course is just a course whose modules contain ORT practice quizzes and the `ort_main` exam. A school biology course is a course with pages, homework assignments and quizzes. Both use the same engine.

**Scope guard.** We still skip Canvas sections, terms, custom roles, Blueprint, SpeedGrader, outcomes, LTI and the inbox. Each can be added later without changing the core tables.
